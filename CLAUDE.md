# ade-ops — Agentic Data Engineering Operations

## What This Is

Local supervisor for remote analytics environments. Single source of truth in `src/`, with overlay-based transforms for multi-environment deployment to Databricks, Fabric, DevOps.

**Key principle**: `src/` is where you author code. `state/` mirrors what's deployed remotely. Overlays handle environment differences declaratively.

---

## Repository Structure

ade-ops has two tiers: a **framework core** (generic, client-agnostic) and **distributions** (per-client customizations that build on the core). A distribution never modifies the core — it consumes it.

```
ade-ops/
├── core/                              # ══ FRAMEWORK CORE (generic, client-agnostic) ══
│   ├── engine/                        # Sync engine (pull/push/diff/status)
│   │   ├── config.py                  # Project config loader
│   │   ├── state.py                   # .state.yaml management
│   │   ├── overlay.py                 # Overlay transforms and assembly
│   │   └── operations.py              # Core operations
│   ├── connectors/                    # Platform connectors (pluggable)
│   │   ├── base.py                    # PlatformConnector protocol
│   │   └── databricks.py              # Databricks workspace API
│   └── templates/                     # Scaffolding for new projects
│
├── distributions/                     # ══ PER-CLIENT CUSTOMIZATIONS ══
│   └── {client}/                      # e.g. reference, demo
│       ├── CLAUDE.md                  # Client-specific instructions (loaded in subdirs)
│       ├── conventions/               # Naming, schema map, guardrails
│       ├── roles/                     # Client-specific role skills (extend core roles)
│       ├── presets/                   # Overlay baselines projects inherit from
│       └── projects/                  # Client projects
│           └── {project}/             # Self-contained project unit
│               ├── src/               # Source of truth (authored here)
│               │   ├── notebooks/
│               │   └── power_bi/
│               ├── overlays/          # Per-env config (catalog, schema, exclusions)
│               ├── patches/           # Temporary per-env overrides
│               ├── state/             # Mirror of remote (pulled, not authored)
│               ├── local/             # Personal, local only
│               ├── shared/            # Team-shared non-deployable (multi-user)
│               └── config/
│                   ├── project.yaml
│                   └── credentials.yaml  # Per-project (GITIGNORED)
│
└── docs/                              # Framework design docs
```

### Framework vs Distribution

| | Framework core (`core/`) | Distribution (`distributions/{client}/`) |
|---|---|---|
| Scope | Generic, client-agnostic | Specific to one client/team |
| Contains | Engine, connectors, generic skills, templates | Client roles, conventions, presets, projects |
| Public-releasable | Yes | No (typically private) |
| Modifies the core? | — | Never. Consumes via roles/presets only |

The `core/` is the asset published as ade-ops. A distribution wraps it with naming conventions, guardrails, and pre-configured roles for a specific client team.

### Key: Self-Contained Projects
Each project under `distributions/{client}/projects/{project}/` is self-contained — its own config, credentials, overlays, and state. It can be moved or detached independently of its distribution.

## Assembly Pipeline

The core concept: `src/` + `overlays/{env}.yaml` + `patches/{env}/` = what gets deployed.

```
src/ (single source)
  → overlay transforms (catalog remap, text replace, exclusions)
    → patches override (temporary env-specific fixes)
      → push to remote
```

## Writing Rules

### Write to `distributions/{client}/projects/{project}/src/` ONLY IF:
- It's source code that should be deployed to environments
- It's the canonical version (environment differences go in overlays)

### Write to `distributions/{client}/projects/{project}/state/` ONLY IF:
- It's a pulled artifact from a remote platform
- Generated by the sync engine (`.state.yaml`)
- **NEVER** manually author files here — they come from `pull`

### Write to `distributions/{client}/projects/{project}/overlays/` ONLY IF:
- It's environment-specific configuration (catalog, schema, exclusions)
- It's declarative transforms, not business logic

### Write to `distributions/{client}/projects/{project}/local/` ONLY IF:
- It's development-only work (setup, utils, experiments)
- It should NEVER be synced to any remote environment

### Write to `distributions/{client}/{conventions,roles,presets}/` ONLY IF:
- It's a client-specific customization (naming rules, guardrails, role pre-configs, overlay baselines)
- It does NOT belong in any other project under that distribution
- It does NOT modify or duplicate framework core code

### Write to `core/` ONLY IF:
- It's framework code (engine, connectors, templates, generic skills)
- It's client-agnostic and reusable across ALL distributions
- It would belong in a public release of ade-ops

### Write to `.claude/agents/{slug}/` ONLY IF:
- It's a **meta-agent** scoped to framework concerns (marketing, governance, research), NOT to a client distribution
- It is single-user single-purpose (lab-only, no DevOps mirror, no multi-author handoff)
- Memory (`CONTEXT.md`, `IDENTITY.md`, `sessions/`) and working state (`drafts/`, `sources/`, `local/`, `handoffs/`) can coexist here while these conditions hold
- Promotion trigger to `distributions/_lab/projects/{slug}/`: a 2nd meta-agent emerges, OR multi-author/shared output is needed, OR the agent's status promotes from `experimental` to `preview`/`stable`

## Operations

Four core operations. Every write to a remote environment requires user confirmation.

| Operation | What it does |
|-----------|-------------|
| `pull` | Download remote state → `state/{env}/` |
| `push` | Assemble src + overlay + patches → upload to remote |
| `diff` | Compare assembled local vs pulled state |
| `status` | Overview: last pull, file counts, patch warnings |

### Safety Protocol

Before ANY remote write (`push`):
1. Assemble files (src + overlay + patches)
2. Show what will change (diff against state)
3. Wait for explicit user confirmation
4. Execute upload
5. Pull to update state

### Operations logging — `ops.log`

Operative skills append a line to the project `ops.log`:

```
{ISO_timestamp} | {role} | {ACTION} | {env|--} | {detail} | {ok|fail}
```

`{role}` is the persona slug **actually active** in the session (`ops-dev`,
`ops-prod`, `ops-operator`, `ops-review`, `ops-manager`, `ddf-operator`, …). If
you are operating **without** a persona — bare Claude invoking task skills
directly — log as `claude-adhoc`. **Never** write a persona slug you are not
operating as: the slug records which role's gates applied, so a forged slug is a
false audit trail. Full convention: [`core/conventions/ops-log.md`](core/conventions/ops-log.md).

## Skill catalog & description standard

Skills are authored **once** in `.claude/skills/<name>/SKILL.md` — the single source of truth (Claude Code native + the Agent-Skills open standard). Two hard requirements for every skill:

1. **Frontmatter `name` + a well-formed `description`.** `description` is not decoration — it is the field cross-harness consumers (Copilot, Codex, …) index on to **discover** and **auto-trigger** a skill. A skill with a missing/weak `description` is invisible or mis-triggered outside Claude Code. Write it as *what it does + when to use it*, never a bare restatement of the title.

2. **Dual catalog — project the source to the vendor-neutral path.** Not every harness reads `.claude/skills/`: Claude Code and Copilot do, but **Codex reads `.agents/skills/`** and does **not** fall back to `.claude/skills/` (validated 2026-07-04). So the source is projected into `.agents/skills/` by [`tools/sync_agent_skills.py`](tools/sync_agent_skills.py). `.agents/` is a **generated artifact** (gitignored) — regenerate after any skill change. Wire it into the pre-commit hook (`.githooks/pre-commit`) and the seat/onboarding launcher so the projection can never drift silently (the drift that made 55/57 skills invisible to Codex on 2026-07-04).

**New-skill checklist:** author in `.claude/skills/` → set `name` + a real `description` (+ `status`, below) → `python -m tools.sync_agent_skills` → `--check` clean.

**Validated (2026-07):** Claude Code + GitHub Copilot (`.claude/skills/`), OpenAI Codex (`.agents/skills/`). **Pending validation:** Cursor (`~/.cursor/skills/`), Google Antigravity (`~/.gemini/config/skills/`), Gemini CLI, Windsurf, Cline — extend `TARGETS` / the launcher when validated. Detail + cross-harness matrix: [`core/conventions/agent-skills-catalog.md`](core/conventions/agent-skills-catalog.md). **Scope:** adopted on the lab and a client distribution; other distributions on-demand.

## Skill maturity convention

Skill files — under `.claude/skills/<name>/SKILL.md` (canonical Agent-Skills folder) or the legacy `.claude/commands/<name>.md` — carry a frontmatter `status:` field that signals the level of confidence in the skill's behaviour. Agents and humans use this signal to calibrate trust. Both locations are honoured by the publish maturity gate; `.claude/skills/` is the migration target (Agent-Skills open standard, read by Claude Code + Copilot/Codex/… — see TICK-010).

```yaml
---
status: preview            # stable | preview | experimental | deprecated
since: 2026-05-24          # date the current status was assigned
deprecated_by: name        # only when status == deprecated
deprecated_on: 2026-MM-DD  # only when status == deprecated
successor_skill: /name     # only when status == deprecated
supersedes_in_part: name   # optional, for partial-supersession transitions
related: a, b, c           # optional, sibling skills the agent should know about
---
```

### Status values

| Status | Meaning | Use |
|---|---|---|
| `stable` | Battle-tested in production by at least one team-member other than the author; documented gotchas all mitigated; no known silent failures. | Default for trusted operative skills. Recommended path. |
| `preview` | Working as designed but not battle-tested. May have rough edges. The skill body should include a "Preview tracking — known unknowns" checklist of things that haven't been verified yet. | New skills, freshly-ported skills, skills wrapping a new engine or pattern. Surface the disclaimer up-front. |
| `experimental` | Significant unknowns or known partial gaps. May change shape between sessions. Not recommended for unattended use. | One-off explorations, throwaway probes, very early ports. |
| `deprecated` | Superseded by `successor_skill`. Body collapsed to a redirect stub. File retained so `/ops-sync` can detect the marker for users on older clones. | Always paired with `deprecated_by` + `deprecated_on` + `successor_skill`. |

### Promotion criteria (preview → stable)

Each `preview` skill defines its own promotion criteria in a "Status — promotion to `stable`" section in the body. Typical criteria:

1. **N distinct real-world uses** (non-synthetic) without manual remediation post-execution. The number depends on the skill's blast radius — 1–3 for low-risk, 5+ for high-impact paths.
2. **All documented gotchas mitigated** (fixed-by-default in the underlying engine, or surfaced explicitly with remediation hint — not silent).
3. **One team member other than the author** has used the skill successfully without coaching from the framework maintainer.

When promotion criteria are met, the skill's frontmatter is updated `status: preview` → `status: stable` in a dedicated commit with a note in `ops.log`.

### How agents should react to status

- `stable`: invoke confidently. Reserve user confirmation for the standard safety gates (push to cert/prod, destructive ops, etc).
- `preview`: invoke when the user asks; mention the `preview` status in the first turn ("⚠️ this skill is in preview — heads up if you see rough edges"); be extra ready to log unexpected behaviours as findings.
- `experimental`: only invoke when the user explicitly asks. Warn that the surface may change.
- `deprecated`: do not invoke. Read the body for the `successor_skill` pointer and propose that one instead.

### Honest disclosure principle

A skill whose status is `preview` or `experimental` should include in its body a section ("Preview tracking" / "Known unknowns") listing specifically **what hasn't been verified yet**. Vague disclaimers are useless; specific bullets calibrate trust correctly. Example: see `/pbir-create.md` "Preview tracking — known unknowns".

## Configuration

### project.yaml — Environment Definitions

```yaml
project:
  name: {project_name}
  client: {client_name}

platforms:
  databricks:
    host: {workspace_url}

environments:
  cert:
    overlay: overlays/cert.yaml
    platforms:
      databricks:
        workspace_path: /path/to/cert
        catalog: {cert_catalog}
        schema: {schema}

scopes:
  notebooks:
    path: src/notebooks
    connector: databricks
```

### Overlay Files — Per-Environment Transforms

```yaml
# overlays/prod.yaml
databricks:
  catalog: silver_prod
  schema: analytics
  workspace_path: /Shared/Project/PROD

transforms:  # optional explicit replacements
  - pattern: "old_value"
    replace: "new_value"

exclude:  # glob patterns to skip
  - "setup/*"
  - "_*"
```

## Code Quality Standards

This is intended as a distributable product. Code must be:

- **Clean**: no dead code, no commented-out blocks, no TODOs in shipped code
- **Typed**: Python type hints on all public functions
- **Documented**: docstrings on public API, not on obvious internals
- **Tested**: connectors and engine must have tests
- **Minimal**: solve the current problem, don't build for hypothetical futures

### Python Style
- Python 3.10+
- Use `pathlib.Path` for all file operations
- Use `pyyaml` for YAML (not custom parsers)
- Use `httpx` for HTTP calls (async-ready)
- Use `click` for CLI (if we build one)
- Connectors implement a common interface (protocol class)
