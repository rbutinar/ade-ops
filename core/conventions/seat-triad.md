# Seat triad — identity, context, ops

> The three layers that together make an ade-ops seat *resumable* and
> *attributable* across sessions, operators, and Claude-agent
> invocations. Documented 2026-05-28 after seat ade-ops-2 surfaced the
> gap during V1 onboarding-track dogfooding.

## The triad

| Layer | Question it answers | Persistence | Where it lives |
|---|---|---|---|
| **Identity** | *Who is this seat?* | Static + event log | `distributions/<dist>/.seat.yaml` (static) + per-line `role` field in `ops.log` (event) |
| **Context** | *What is the state, and what was the last reasoning?* | Durable, narrative | `distributions/<dist>/.seat-sessions/YYYY-MM-DD_<topic>.md` (per-session) + agent CONTEXT.md (per-agent-role) |
| **Ops** | *What actions have been taken, with what outcome?* | Append-only audit | `<project>/ops.log` (per-project) + `docs/ops.log` (framework-level, lab only) |

The three layers are complementary, not redundant:

- **Identity** without ops = static manifest, says nothing about
  activity.
- **Ops** without context = audit trail with no story — you can
  reconstruct *what* happened but not *why*.
- **Context** without identity = anonymous narrative — you can read
  the recap but cannot attribute or coordinate.

## Mental model — the seat is the software, the public repo is the channel

The triad is coherent under a specific framing: the public ade-ops
repository is a **release channel** (delivery of framework updates),
not a shared git workspace. The seat is the **framework installed
locally**, with its own user data. Mapping:

| Concept | Traditional git workspace | ade-ops release channel |
|---|---|---|
| Public repo | Shared state, all clones are copies | Release delivery channel |
| Seat | A copy of the shared state | Local install with persistent user data |
| `/ops-publish` orphan | (n/a) | New version pushed to channel |
| `git fetch && reset --hard origin/main` | History-rewriting catastrophe | `apt upgrade` of the framework |
| The triad (gitignored) | (n/a) | User data partition — survives every upgrade |
| CHANGELOG.md | Optional add-on | Release notes |

This is why the triad is **gitignored by design**: it is user data,
not framework code. The framework code is rebuilt fresh on every
release; the user data persists across updates. Working tree dirty is
the analogue of "unsaved document on app update" — handled by stash
prompts, not by merging.

Operators expecting standard git semantics experience disorientation
when they see force-push + orphan history (an empirical case from
ade-ops-2 on 2026-05-28). Operators using the release-channel mental
model see the same operation as routine.

## Why this matters

A seat is a long-lived (clone, distribution) pair operated by humans
and/or Claude-agents across many sessions. The triad lets the seat
*resume itself*:

1. **Boot continuity**: when an operator (human or agent) opens the
   seat next, reading the last session log + the open findings yields
   a complete picture in under a minute. No "where was I" cost.

2. **Cross-operator handoff**: when a different operator (or agent)
   takes over the seat, the triad supplies attribution + state without
   requiring a synchronous handoff conversation.

3. **Promotion-criteria evidence**: skill promotion (`experimental` →
   `preview` → `stable`) needs evidence of *distinct seats* having
   exercised a skill. The triad provides that evidence, scoped per
   seat, audit-friendly.

4. **Honest failure reporting**: granular ops.log outcomes (not just
   "ok"/"fail" but "partial: 2/5, failed: 3 paths") prevent the
   "looks-green-but-isn't" failure mode that surfaced via ade-ops-2
   dogfooding on 2026-05-27.

## Layer detail

### Identity — `distributions/<dist>/.seat.yaml`

Static schema. See [`core/conventions/seat.md`](./seat.md) for full
detail. Key idea: seat = *(clone, distribution)* pair, with roles
declared explicitly. The roles drive governance (PR-only vs direct
commit) and feed feedback attribution.

The *event* dimension of identity lives implicitly in `ops.log`: the
`role` field on each line records which role authored the action. This
is set via the `ADEOPS_ROLE` env var by operator skills (`/ops-dev`,
`/ops-prod`, `/ops-review`).

### Context — session log + agent CONTEXT

Two surfaces by design:

- **Per-session log** at `distributions/<dist>/.seat-sessions/...md`
  generated by [`/ops-session-close`](../../.claude/commands/ops-session-close.md).
  Captures one session's worth of narrative (goal, outcome, commits,
  findings, state, next entry point). Gitignored — durable but local
  to the seat.

- **Per-agent CONTEXT.md** at `.claude/agents/<role>/CONTEXT.md`
  (e.g. `ops-manager/CONTEXT.md`). Captures cross-session continuity
  for one Claude-agent role. Committed to the framework repo (no
  client-sensitive content).

Overlap is acceptable: the per-session log is *episodic*, the
per-agent CONTEXT is *cumulative*. The first is read at seat boot;
the second is read at agent boot.

### Ops — per-project + framework `ops.log`

Format (one line per action):

```
{ISO8601} | {role} | {OP} | {env} | {scope}: {detail} | {outcome}
```

Where `outcome ∈ {ok, fail, partial, empty}`. The `partial` outcome
is the post-2026-05-28 fix: actions that mix success and failure
(e.g. PUSH that uploaded 2 of 5 files) report `partial` with detail
`2/5 — failed: 3` instead of the previously misleading `ok`.

Two scopes:

- **Per-project ops.log** at `{project}/ops.log` (gitignored or
  committed depending on distribution policy). Captures pull / push /
  diff / status invocations on this project.

- **Framework ops.log** at `docs/ops.log` (lab-only, never published).
  Captures framework-level operations: engine fixes, skill creation,
  cross-repo coordination, etc. Maintained by `/ops-manager`.

## Boot UX — what an operator sees on seat open

When an operator (or agent) starts work on a seat, the host skill
(`/ops-dev`, `/ops-prod`, `/ops-review`, or the agent's startup step)
performs:

1. **Read identity** — load `.seat.yaml` to surface seat name + role
   + distribution.
2. **Read context** — find the most recent session log in
   `.seat-sessions/`; if its frontmatter `status: in_progress` or
   `unresolved_*` > 0, surface a one-line summary.
3. **Read ops** — tail the last N lines of `ops.log` to show recent
   activity + any partial/fail outcomes that need attention.
4. **Surface** a short briefing: "Seat `<name>`. Last session
   `<date>_<topic>` left <X> findings open and <Y> commits shipped.
   Last ops.log tail shows <recent activity>. Resume from
   `<next_entry_point>`?".

This briefing is the "magical" experience equivalent to what
`/ops-manager` already does at boot — extended to all seat operators.

## Anti-goals

- **No central seat registry in the lab**. Each seat self-describes
  via its local manifest + session logs. Identity correlation happens
  at audit time (the framework manager can read ops.log entries
  written by multiple seats), not at runtime.

- **No automatic session-close**. Operators close sessions explicitly
  via `/ops-session-close`. Auto-detection of "session ended" leads
  to either too-eager closes (noisy) or stale `in_progress` states
  (dishonest). The manual close + frontmatter `status` field is a
  better trust signal.

- **No coupling between layers**. Identity can be edited without
  touching session logs; ops.log entries are append-only and never
  rewritten by session-close; session logs are derived but not
  authoritative — `ops.log` remains the audit ground truth.

## Seat modalities — operator vs canary

A seat can operate in two complementary modalities. The triad layers
are the same; the policy on the user-data partition differs.

### Operator mode (long-lived)

The default modality. The seat accumulates session logs (`.seat-sessions/`),
identity manifest (`.seat.yaml`), and per-project `ops.log` over time.
Daily operations are fluid because every session boot reads the
accumulated context.

- Reset policy: only `git fetch && git reset --hard origin/main` —
  preserves all user data
- Typical roles: `maintainer`, `primary-tester`, `contributor`,
  `observer`
- Purpose: exercise the framework with continuity; demo live
  capability with prior context loaded

### Canary mode (ephemeral)

A seat configured with role `onboarding-canary`. Its purpose is to
re-validate the first-arrival experience: each test cycle starts from
zero state, no carry-over from previous runs.

- Reset policy: `scripts/factory-reset.ps1` before each cycle (soft
  reset — wipes user-data partition) OR `scripts/fresh-install.ps1`
  (hard reset — re-clones the seat from scratch)
- Typical role: `onboarding-canary` (single-purpose, not stacked)
- Purpose: catch onboarding regressions, verify repo cleanliness,
  validate that the framework discovers itself without prior context

### Soft reset vs hard reset — which one when

| Aspect | Soft reset (`factory-reset.ps1`) | Hard reset (`fresh-install.ps1`) |
|---|---|---|
| Wipes user-data partition | ✅ yes | ✅ yes (whole dir gone) |
| Resets `.git/` history | ❌ no — same `.git` objects + refs accumulate over time | ✅ yes — fresh clone, only one orphan commit visible |
| Resets filesystem metadata / orphan files | ❌ no — NTFS attributes, hidden files, accidental orphans survive | ✅ yes |
| Resets user-scope memory in `~/.claude/projects/<slug>/` | Optional flag in script | ✅ yes (deleted with the dir) |
| Time per cycle | ~30 seconds | 2-5 minutes (clone + initial install) |
| Typical use | Daily UX iteration (95% of cases) | Sanitization audit / leak verification (5% of cases) |

Default for daily onboarding iteration: **soft**. Default for
pre-release security check or post-`/ops-publish` cleanliness
verification: **hard**.

The two scripts ship under the project's `scripts/` directory in
the reference distribution. Other distributions may provide their own
flavours but the naming convention (factory-reset / fresh-install) is
consistent across distributions.

### Pairing modalities with audience

A team running ade-ops typically maintains:

- One or more **operator seats** for daily work (one per maintainer /
  primary-tester)
- At least one **canary seat** for onboarding tests, especially
  before scheduled releases or demo sessions

The framework manager exercises canary mode before any go-public-style
event (orphan release + community announcement). Operators exercise
operator mode in their day-to-day cycles.
